Goal trips-db-landing-invites (shipped to branch feat/trips-db-landing-invites, 2026-11-05).

Outcome: per-trip persistence in Azure SQL (dbo.user_trips, version column, optimistic concurrency with 409 VERSION_CONFLICT), migration 002 backfilling the legacy one-blob-per-user dbo.trips (kept for rollback), client save engine that retries on database-waking/network errors with backoff (5s→60s cap, Retry-After honoured) plus beforeunload guard, legacy localStorage import on every login via POST /api/trips/import, "download all" backup + per-trip download, a signed-out marketing landing page, public invite requests (honeypot, salted IP-hash rate limit, silent duplicates, admin email), and an admin Access requests screen that emails single-use 14-day invite codes (stored as SHA-256 hashes; register consumes them in one T-SQL batch).

Root cause of "trips are not saved": the old client showed a banner on a database-waking save failure but never rescheduled the save (serverless Azure SQL auto-pause), so edits were lost on reload.

Key decisions: admins via ADMIN_EMAILS app setting (not a roles table); single-use codes alongside the shared INVITE_CODE; landing shown by auth state (no router); imported files always become new trips.

Remember next time: migration 002 must be applied to Azure SQL (scripts/db-migrate.sh) before deploying the API; follow-ups.md in the goal folder lists 30+ backlog items (timing side channel on invite requests, created-then-deleted trip reappearing, sign-out dropping failed edits).
