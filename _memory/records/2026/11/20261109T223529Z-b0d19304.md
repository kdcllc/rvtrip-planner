Goal custom-email-domain (shipped to branch feat/custom-email-domain, 2026-11-09): send app email from rvtrip@moedim.dev (display name "RV Trip Planner") instead of the Azure-managed DoNotReply@<guid>.azurecomm.net.

How it works:
- communication-services.bicep adds an optional CustomerManaged ACS domain plus a senderUsernames child, next to the always-kept AzureManagedDomain.
- The string param useCustomEmailDomain ('false' by default) chooses linkedDomains and the senderAddress output. The domain has to be DNS-verified before the toggle is turned on, otherwise the ACS PUT fails.
- A new module, email-dns-records.bicep, is deployed cross-RG into the existing Azure DNS zone moedim.dev in moedim-rg. It writes the apex @ TXT set as union(existingApexTxtValues, [ms-domain-verification]) and two DKIM CNAMEs.
- The deployment fully owns the apex TXT set. main.bicep's existingApexTxtValues default holds the 4 live values (MS=, M365 SPF, an unknown token, google-site-verification). The existing M365 SPF already contains include:spf.protection.outlook.com, so SPF is not rewritten.
- The azd postprovision hook scripts/acs-verify-domain.sh runs `az communication email domain initiate-verification` for any of Domain/SPF/DKIM/DKIM2 that is not Verified, and always exits 0. In CI it skips, because az is not logged in there (azd-only login).
- Rollout: provision with the toggle off, wait for Verified, then run `azd env set USE_CUSTOM_EMAIL_DOMAIN true` and provision again. CI has a repo variable USE_CUSTOM_EMAIL_DOMAIN.
- The CI federated identity needs DNS Zone Contributor on moedim-rg. That is a user step.

API code is unchanged; it reads ACS_SENDER_ADDRESS.
