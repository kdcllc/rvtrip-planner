Pitfall: in-memory SQL fakes in api/src/__tests__ (security-regression, auth-flow integration) dispatch on statement-prefix regexes and bound params, not on WHERE clauses.

Consequences seen in goal trips-db-landing-invites: (1) a new multi-statement batch (register with single-use invite code, starting "SET XACT_ABORT ON; BEGIN TRAN; DECLARE @req TABLE") made an unrelated security test return 500 because the fake threw "unhandled statement" — the file was outside the implementing task's write fence, requiring a corrective task; (2) deleting "user_id = @userId AND" from real SQL text left the integration suites green — only SQL-text assertions in trips.test.ts caught it.

How to avoid: when a task introduces new SQL statement shapes, give it (or an ordered sibling task) ownership of every shared test fake that must recognise them; keep SQL-text assertions for scoping clauses in unit tests; and lint the whole repo (npm run lint) in at least one acceptance criterion so unused-import errors in rewritten test files do not reach the final audit.
