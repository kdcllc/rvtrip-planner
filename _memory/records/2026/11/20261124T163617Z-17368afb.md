Pitfall: cleaning secrets out of git history for a repo that will go public.

What went wrong (caught in planning): two assumptions were false. First, force-pushing rewritten branches does not remove old commits from GitHub — every pull request keeps its commits reachable under refs/pull/*, so leaked files stay fetchable. The rewritten history has to go to a new or recreated repository (or GitHub Support must purge the refs). Second, a gitleaks CI job that scans full history goes red on every run until the rewrite is done, which invites someone to make it non-blocking; scan only the commit range of each PR or push, and run the full-history scan once on the rewritten result.

How it was detected: scouting history with git log --all for added .env and .azure paths before planning, and the goal evaluator counting commits that touch those paths.

How to avoid it: before any public release, list sensitive filenames ever added (git log --all --diff-filter=A --name-only), treat every leaked credential as compromised regardless of the rewrite, and note that gitleaks exits 0 when git rejects a revision range, so verify range SHAs exist before trusting a green scan.
